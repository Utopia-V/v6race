# v6race 原理

## 问题：约一半的 IPv6 连接无法建立

笔者所在高校的宿舍 Wi-Fi 会自动分配教育网 IPv6 地址，无需登录。2026 年 10 月的测量结果如下：

| 测试 | 结果 |
|---|---|
| 到网关的 `ping -6` | 15/15 |
| 到中科大镜像站的 `ping -6`，16 个独立进程各发 4 个包 | 64/64 |
| 单个 TCP 连接（清华、中科大镜像站等） | 成功率 50%–60% |
| 到阿里 DNS 的 IPv6 UDP 查询 | 成功率约 60% |
| 连接建立后的下载速度 | IPv6 12–23 MB/s，IPv4 1.2 MB/s |

ICMP 全部可达，TCP 和 UDP 则按连接随机失败。这说明问题既不在无线信号，也不在本机，而是路径上的一台有状态设备在随机拦截新建的会话。失败有两种表现：一种是数据包被丢弃，握手超时；另一种是约一个往返时间后收到拒绝。重传 SYN 不能挽回失败的连接，一个会话一旦被判定为异常，它的所有数据包都无法通过。已经建立的连接则始终稳定。

你可以用以下命令判断自己的网络是否属于同一情况：

```sh
ping -6 -c 20 mirrors.tuna.tsinghua.edu.cn          # 基本不丢包
for i in $(seq 20); do curl -6 -s -o /dev/null -m 3 https://mirrors.tuna.tsinghua.edu.cn/ && echo -n o || echo -n x; done
```

如果第二条命令的输出中 o 和 x 随机交错，即属于这种情况。

## 竞速为何有效

各个新连接的成败互不相关，这一点可以直接验证。成功和失败在时间上随机交错；用本机的 IPv6 地址持续向网关发送保活包，成功率也没有变化（31/60 与 28/60）。同时发起 4 个连接并选用最先成功的一个，20 次中成功 19 次，而单个连接只成功 12 次。

设单个连接的成功率为 p，同时发起 k 个连接，全部失败的概率为 (1−p)^k。p = 0.5 时，4 个连接全部失败的概率约为 6%，8 个约为 0.4%。因此 v6race 先发起 4 个连接；如果 1 秒内没有成功，或者这 4 个已经全部被拒绝，再补充 4 个；3 秒仍未成功则放弃 IPv6。落选的连接可能也已完成握手，但程序的数据只发给最先建立的连接，其余连接随即关闭。

## Linux：在内核中透明接管

程序照常调用 `connect()`，无需知道 v6race 的存在。一个连接依次经过以下步骤：

1. **设置标记**。nftables 的 output 链（route 类型，mangle 优先级）发现一个发往公网 IPv6（2000::/3）的新 TCP 连接后，为其 conntrack 记录设置标记，该连接去程方向的每个数据包都带上 fwmark 0x7672。route 类型的链会使内核按新标记重新查询路由。
2. **送回本机**。ip rule 4991 使带 0x7672 的数据包查询路由表 7672。该表只有 `local ::/0` 路由，数据包因此被视为发往本机，经 lo 回到协议栈。
3. **交给 v6race**。prerouting 链中的 TPROXY 将数据包交给 v6race 开启了 `IPV6_TRANSPARENT` 的监听 socket。v6race 通过 `accept()` 得到的连接，其本地地址就是程序原本要连接的地址，可以用 `getsockname()` 读出。
4. **竞速与转发**。v6race 向该地址发起竞速，连接建立后在程序与目标之间转发数据。

v6race 自身的连接带有另一个标记 0x7673。output 链对其直接放行，ip rule 4990 使其查询 main 表。这条规则优先于代理软件的策略路由，因此代理软件的 TUN 不会截获这些连接。Wi-Fi 重连期间，main 表可能暂时没有默认路由，此时 ip rule 4992 将带 0x7673 的数据包判为不可达，避免其继续向下匹配而进入代理软件的 TUN。

**绑定网卡的 socket。** 代理软件（例如开启了 `auto-detect-interface` 的 Mihomo）会将自己的出站 socket 绑定到物理网卡（`SO_BINDTODEVICE`）。这类 socket 查询路由时只匹配该网卡上的路由，表 7672 中位于 lo 的路由对它们无效，数据包会直接从网卡发出而绕过 v6race。因此，表 7672 在默认 IPv6 网卡上也添加一条 `local ::/0`（metric 100）。默认网卡可能变化，例如开机时 Wi-Fi 尚未连接，或改用有线网络；网卡断开时，内核也会删除这条路由。所以 v6race 每 10 秒按当前的默认 IPv6 网卡核对一次，必要时补充或更正。

**竞速全部失败时的处理。** 程序一侧的 TCP 握手由本机内核完成，程序此时已认为连接建立。如果直接断开，程序看到的是“连接建立后被重置”，浏览器不会因此改用 IPv4。因此 v6race 等待程序发出首个数据包：HTTPS 的 TLS ClientHello 以明文携带目标域名（SNI），HTTP 请求带有 Host 头。读出域名后，v6race 自行改用 IPv4 连接。对于无法读出域名的协议（例如 ssh），竞速全部失败时只能断开连接。

**整段地址不可达。** 部分境外站点的 IPv6 地址在这条路径上完全不通。实测中，Google 和 Facebook 的 8 个并发连接全部失败，Cloudflare 则可以连通。如果一轮竞速中的连接全部没有回应，v6race 会记录这个 /64 地址段，10 分钟内改用 IPv4，以免每次都等待 3 秒；前提是能从首个数据包中读出域名，否则仍会竞速。有两种情况不做记录：每个连接都被明确拒绝，说明网络可达而端口未开放；失败是因为本机暂时没有网络（Wi-Fi 重连期间报告“网络不可达”，或 DNS 完全没有回应），说明不了目标的状况。网络恢复后，v6race 立即照常尝试。

**UDP 与 QUIC。** UDP 没有内核可以识别的握手，v6race 无法替程序挑选一个可用的会话。QUIC 的连接建立与 TLS 握手是同一个加密握手，在程序进程内完成，中间环节无法单独完成“建立连接”这一步。因此 v6race 默认对发往公网 IPv6 的 UDP 443 返回“不可达”，浏览器随即改用 TCP，而 TCP 连接会参与竞速。

**退出时的还原。** systemd 服务退出时（包括崩溃），由 `ExecStopPost` 运行 `v6race.cleanup` 删除全部规则。清理只依赖标准库和服务启动时记录的参数（`/run/v6race/rules.json`），配置文件损坏也不影响清理。即使 v6race 已停止而规则残留，IPv6 TCP 连接也只会失败，程序随即改用 IPv4，结果是网速较慢，而不是无法上网。安装脚本先用服务实际使用的解释器检查新版本的代码、配置和规则，再由旧版本停止旧服务，确认规则已全部清除后才切换版本。

## Linux：与 Mihomo 配合

Mihomo 开启 TUN 时，程序得到的都是 fake-ip 地址，连接全部进入 Mihomo，由 Mihomo 连接直连的网站。要让这部分直连使用 IPv6，需要以下两项设置：

- `dns.ipv6: true`：Mihomo 解析域名时保留 IPv6 地址。在 fake-ip 模式下，程序仍然只得到 fake-ip 形式的 IPv4 地址，规则不受影响。
- `tcp-concurrent: true`：Mihomo 同时连接 IPv4 和 IPv6 地址，并使用最先建立的连接。v6race 在本机立即接受连接，因此 IPv6 通常最先建立；随后 v6race 才与真正的目标竞速，这是两个独立的阶段。被 Mihomo 放弃的连接如果在发送任何数据之前关闭，v6race 会取消相应的竞速。

**一次循环故障。** 账号风控严格的网站（支付、银行等）最初只列在 v6race 的 IPv4 名单中，结果形成了循环。Mihomo 用 IPv6 连接支付宝，连接被 v6race 接管；v6race 改用 IPv4 时查询 DNS 失败（校园网拦截公共 DNS），于是按域名交回 Mihomo；Mihomo 再次使用 IPv6，连接又回到 v6race。防循环的锁只在等待 Mihomo 确认连接成功的瞬间生效，而 Mihomo 的 IPv6 连接被 v6race 在本机立即接受，确认几乎即时返回，锁随即释放。几秒内打开的连接超过 1024 个，进程的文件描述符耗尽，所有经过 v6race 的连接都无法继续。

修正包括三项。第一，名单中的网站在 Mihomo 中改用只使用 IPv4 的直连出站（`type: direct, ip-version: ipv4`），Mihomo 不再为它们发起 IPv6 连接。第二，回退时先查询网络分配的 DNS 服务器（校园网 DNS），1 秒内没有回答才查询公共 DNS。第三，防循环的锁改为在连接存活期间计数，同一网站最多允许 8 条连接同时经 Mihomo 回退。回流的连接与正常的新连接无法区分，这一上限使循环最多持续 8 层即停止，同时不会拒绝正常的并发连接。此外，服务同时处理的连接数上限为 4096，文件描述符上限为 65536，以留出余量。

## Windows：本机代理

Windows 没有 nftables、TPROXY 和 Linux 式的策略路由。透明接管需要 WinDivert 一类的抓包驱动，要求管理员权限，复杂度也高得多。因此 Windows 版以本机代理的方式工作，在 `127.0.0.1:10800` 同时接受 SOCKS5 和 HTTP 代理请求。代理请求通常携带域名，回退时无需读取 SNI。

- **自行查询 DNS。** 代理软件开启 TUN 时，系统 DNS 返回的是 fake-ip 地址，公共 DNS 又被校园网拦截。因此 v6race 直接查询网卡上配置的 DNS 服务器（通常是 DHCP 分配的校园网 DNS），1 秒内没有回答才查询公共 DNS。v6race 先查询 IPv6 地址，没有 IPv6 地址或竞速失败时再查询 IPv4 地址。代理请求必须携带域名：如果 SOCKS5 客户端先在本地解析、只发送 IP 地址，v6race 就无法按域名回退。命令行中应使用 `socks5h://` 而不是 `socks5://`。
- **出站绑定物理网卡。** v6race 通过 `IP_UNICAST_IF` 和 `IPV6_UNICAST_IF` 使自身的连接从物理网卡发出，代理软件的 TUN 无法截获。代理软件本身也采用这一方法避免循环。
- **网卡的选择。** 启动时调用一次 PowerShell 的 `Get-NetIPConfiguration`，只在物理网卡（`HardwareInterface`）中选择有默认网关的一块，优先选择具有 IPv6 地址的网卡。TUN、VPN、Hyper-V 等虚拟网卡不会被选中。
- **系统代理。** 只有在未检测到代理软件、系统代理和 PAC 均未被占用、并且能够监听窗口关闭事件时，v6race 才将系统代理设为自身。为避免系统代理指向已关闭的端口而导致无法上网，操作顺序是固定的：先用按用户会话区分的互斥量确保只有一个 v6race 在运行；再恢复上次未清理的系统代理，这一步不需要联网，也不读取配置文件；然后绑定监听端口；最后才修改系统代理。修改之前，原有设置先写入 `%LOCALAPPDATA%\v6race\proxy-backup.json`，同时在注册表 `RunOnce` 中登记“下次登录时恢复”；如果恢复命令失败，Windows 会保留该项并在下次登录时重试。启用代理时最后才打开开关，恢复为关闭状态时首先关闭开关，因此写入中途失败也不会留下“已启用但指向无效端口”的状态。正常退出或关闭窗口时，系统代理立即恢复；注销、关机、断电或进程被强制结束时，在下次登录或下次启动 v6race 时恢复。恢复只在系统代理地址仍为 v6race 时进行，用户之后自行设置的代理不会被覆盖。以下地址不经过代理：`localhost`、`127.*`、`10.*`、`172.16.*` 至 `172.31.*`、`192.168.*`。以域名访问的校园网站点（例如登录页面）经过 v6race，同样可以正常打开。
- **普通 HTTP 请求。** 对于 `GET http://host/path` 形式的请求，v6race 将其改写为 `GET /path`，按请求行中的地址重新生成 `Host` 头，并加上 `Connection: close` 后转发。服务器响应完毕即关闭连接，浏览器的下一个请求使用新连接。WebSocket 升级请求保留原有的 `Connection: Upgrade`，升级后按隧道转发。

## 固定使用 IPv4 的网站

改用 IPv6 后，直连网站看到的是你自己的教育网 IPv6 地址，而不是众多用户共用的校园网 IPv4 出口；回退时，网站看到的又是 IPv4 地址。两个地址属于同一所学校、同一座城市，大多数网站不会因此采取措施。支付、银行、主要购物网站、12306 和战网国服对账号的风控更为严格，默认固定使用 IPv4，网站看到的出口与以前相同。名单见 `src/v6race/config.py` 中的 `DEFAULT_V4_ONLY`，可以在配置中替换。

在代理模式下，只要客户端传来的是域名，v6race 在建立连接之前就能得知域名，名单必定生效。透明模式则需要从首个数据包中读取域名，如果该数据包比竞速结果晚到 0.3 秒以上，名单便来不及生效。因此，开启 Mihomo 时建议同时把名单写入 Mihomo 的规则（示例见 README），让 Mihomo 在建立连接之前就固定使用 IPv4。

## 局限

- 只对支持 IPv6 的网站有效。仅有 IPv4 地址的网站仍然使用被限速的 IPv4。
- UDP 不参与竞速，也不会加速。Linux 透明模式默认拒绝发往公网 IPv6 的 UDP 443（QUIC），使浏览器改用 TCP；游戏、语音等其他 UDP 流量不受影响。
- Windows 版只覆盖遵循系统代理或代理软件规则的程序。
- 在透明模式下，无法读出域名的协议（例如 ssh）在竞速全部失败时只能断开，不能回退到 IPv4。在代理模式下，只要客户端传来域名就能回退。
- 透明模式只从首个 TLS 记录中读取 SNI。浏览器的 ClientHello 都位于一个记录中；将其拆分为多个记录的客户端无法回退。
- 如果客户端以流水线方式发送普通 HTTP 代理请求（主流浏览器默认不这样做），第二个请求会被转发给第一个网站。
- 透明模式会接管本机发往公网 IPv6 的全部 TCP 连接，包括原本经由 Tailscale 出口节点或 VPN 的连接。使用这类路由时，请先停止 v6race。
- Windows 版的“下次登录时恢复”指向 exe 当前所在的位置，exe 被移动或删除后不再生效。
- IPv6 的速度随时段变化，2026 年 10 月测得 2.5–23 MB/s，均高于被限速的 IPv4。
